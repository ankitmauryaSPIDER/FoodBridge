# FoodBridge Deployment Notes

## Deploy with Vercel, Render and TiDB Cloud

The repository includes a Render Blueprint at `render.yaml` and Vercel SPA routing at `frontend/vercel.json`.

### 1. Prepare TiDB Cloud

1. Create a **MySQL-compatible TiDB Cloud Starter** cluster and enable its public endpoint.
2. Create the `foodbridge` database, and configure the endpoint's IP access list to allow Render's outbound IP addresses. Do not use an unrestricted `0.0.0.0/0` rule for a public production database.
3. Copy the cluster host, port, username and password from TiDB's connection dialog. Starter clusters require TLS; use `sslMode=VERIFY_IDENTITY` in the JDBC URL.

The database URL format is:

```text
jdbc:mysql://<tidb-host>:4000/foodbridge?sslMode=VERIFY_IDENTITY
```

### 2. Deploy the backend to Render

1. Push this project to a Git provider and create a Render Blueprint from the repository root using `render.yaml`.
2. Render builds `backend/Dockerfile` and deploys the API using the `prod` profile. Keep the free plan in mind: the service can sleep when idle and its local filesystem is ephemeral.
3. Set the Blueprint's prompted environment variables:
   - `DB_URL`: TiDB JDBC URL above.
   - `DB_USERNAME` and `DB_PASSWORD`: TiDB connection credentials.
   - `FRONTEND_URL`: the exact production Vercel origin, such as `https://your-project.vercel.app` (no trailing slash).
   - `ADMIN_EMAIL`: email for the initial administrator.
   - `ADMIN_PASSWORD`: unique password of at least 16 characters.
   - `JWT_SECRET` is generated by Render. Keep it private; changing it invalidates existing login tokens.
4. On first startup, Flyway creates the schema and the backend creates the configured admin account. Changing `ADMIN_PASSWORD` later does not change an existing account's password. Verify `https://<render-service>.onrender.com/api/health` returns `{"status":"UP"}`.

### 3. Deploy the frontend to Vercel

1. Import the same repository into Vercel and set **Root Directory** to `frontend`.
2. Use the Vite defaults: build command `npm run build`, output directory `dist`.
3. Add `VITE_API_BASE_URL` to the Vercel production environment, with the Render API URL ending in `/api`, for example `https://<render-service>.onrender.com/api`. Re-deploy after adding it. Production builds fail if this value is missing.
4. Copy the deployed Vercel origin into Render's `FRONTEND_URL` and redeploy the API if needed.

### Free-tier limitations

- Render free services may sleep and have ephemeral storage. Uploaded images stored on the API filesystem can disappear after restarts or redeploys; use object storage before relying on persistent uploads.
- Check TiDB Cloud's current Starter limits and public-endpoint firewall requirements. If Render's outbound IP ranges cannot be allowlisted on your selected plan, do not make the database publicly accessible to all IPs; choose a hosting/database network option that supports restricted connectivity.
- This setup is suitable for a demo, not a high-availability production launch. Confirm backups, quotas, latency, costs and provider terms before real users depend on it.

## Local deployment with Docker Compose

From the project root:

```bash
docker compose up --build
```

Frontend: `http://localhost:5173`

Backend: `http://localhost:8080`
Health check: `http://localhost:8080/api/health`

Stop without deleting persisted data:

```bash
docker compose down
```

Delete local database and images (destructive):

```bash
docker compose down -v
```

## Public deployment checklist

The included compose file is designed for local demonstration. Before a public deployment:

1. Create a managed MySQL-compatible database (the documented setup uses TiDB Cloud Starter) and create/configure a database user with permission to apply schema migrations.
2. Deploy the Spring Boot backend to a Java 21 container host.
3. Activate the `prod` Spring profile and set `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`, `FRONTEND_URL`, `ADMIN_EMAIL` and `ADMIN_PASSWORD` as provider secrets/configuration.
4. Use a cryptographically random JWT secret of at least 32 bytes; never reuse the local development secret.
5. Configure persistent or object storage for uploads. Local filesystem uploads may be lost on ephemeral hosting.
6. Build and deploy the frontend as a static Vite site. Set `VITE_API_BASE_URL` to the HTTPS backend URL ending in `/api`.
7. Configure strict CORS for the exact frontend origin.
8. Use HTTPS for both services.
9. Keep production credentials unique and do not use local demo accounts.
10. Configure backups, logs, monitoring, abuse controls, operational support and food-safety processes.

The `prod` profile requires `JWT_SECRET`, `FRONTEND_URL`, `ADMIN_EMAIL` and `ADMIN_PASSWORD`, validates the schema after applying Flyway migrations, and does not seed demo accounts.

## Hosting notes

This project configuration does not create a public deployment or provision hosting accounts.
